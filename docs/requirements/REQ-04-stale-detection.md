## 1. 背景与目标

章节发布后，作者常会继续改稿（修错字、调情节）。如果忘了同步到平台，读者看到的就是旧版本。平台需要在**本地改稿后自动提示"需更新"**。

**目标**：发布时记录当时正文的 hash；之后本地内容变化即判定为"需更新"，无需人工维护。

## 2. 用户故事

- 作为作者，我改了已发布的章节后，希望平台自动提醒我这一章在某平台上已落后。
- 作为作者，我只是改了换行或首尾空格时，不希望被误报。
- 作为作者，我把新版本更新到平台后，想一键确认，让提示消失。
- 作为作者，我想在看板上一眼看到每本书有多少章待更新。

## 3. 范围

### 3.1 包含
- "需更新"的判定规则（计算态）
- hash 归一化规则（防止误报）
- 状态的展示、筛选、清除（标记已发布）
- 与看板计数的口径统一

### 3.2 不包含
- 展示"改了什么"的内容 diff（后续可做，见 Q3）
- 保存历史版本
- 与平台线上实际内容比对（无 API）
- 主动通知/推送（仅界面提示）

## 4. 业务规则与口径

### 4.1 判定规则（核心）

```
需更新(chapter, platform) :=
    publication.status IN ('pending_review', 'published')
    AND publication.published_hash ≠ chapter.content_hash
```

| 条件 | 结果展示 |
|---|---|
| 无发布记录 / `status = unpublished` | 未发布 |
| `pending_review` 且 `published_hash = content_hash` | 审核中 |
| `published` 且 `published_hash = content_hash` | 已发布 |
| `pending_review` 或 `published`，且 `published_hash ≠ content_hash` | **需更新** |
| `chapter.file_missing = true`（不论上面） | 文件丢失（优先级最高，不判定需更新） |

**关键约束**
1. "需更新"**不入库**，每次查询时计算，保证与内容永远一致。
2. 判定按**章节 × 平台**独立：同一章在番茄已更新、在起点未更新，则起点显示"需更新"。
3. 若 `published_hash` 为空（异常数据，如手工改库）而 `status` 为审核中或已发布，按"需更新"处理（保守）。

### 4.2 业务规则

1. **归一化范围**：hash 基于「发布形态」——标题 + 转换后的正文（REQ-02 F2.11）。换行符、首尾空白、仅 Markdown 写法不同而发布文本相同的改动，不触发需更新；标题、正文文字、标点、行内空格的变化会触发。
2. **数据新鲜度**：外部编辑器改稿后，在下次"打开页面/重新扫描"同步前，`content_hash` 尚未更新，"需更新"不会出现。这是 MVP 的已知行为，页面上"重新扫描"按钮是显式刷新入口。
3. 标记已发时，若文件在同步之后又被外部修改过，则 `published_hash` 记录的是库中（较旧）hash。为降低此风险，标记已发前建议先对该章做一次单章同步（见 Q1）。
4. 不因"取消已发"保留 `published_hash`（REQ-03 F3.14）。

## 5. 功能需求

| 编号 | 需求 |
|---|---|
| F4.1 | 提供纯函数 `isStale(chapter, publication)`，位于 `lib/publish.ts`，输入章节与发布记录，返回布尔；无副作用，便于单测。 |
| F4.2 | hash 由 `lib/hash.ts` 提供：SHA-256(标题 + `\n` + 发布形态正文)；发布形态转换由 `lib/publish.ts` 提供并被 REQ-05 复用（与 REQ-02 F2.11 同一实现，不得出现两套逻辑）。 |
| F4.3 | "标记审核中/已发布"、"重新提交（覆盖）"时，把 `published_hash` 置为**该时刻**的 `chapter.content_hash`（REQ-03 F3.13/F3.15）；审核中→已发布不改该值。 |
| F4.4 | 章节保存或同步导致 `content_hash` 变化后，无需额外动作，下次渲染即自动呈现"需更新"。 |
| F4.5 | **自愈**：用户改稿后又改回原样，`content_hash` 回到 `published_hash`，"需更新"自动消失。 |
| F4.6 | 详情页徽标以橙色"需更新"展示；悬浮提示："本地内容已于 {时间/或：已变更}，与 {平台} 已发版本不一致"。（"变更时间"取章节文件修改时间，若不可得则省略。） |
| F4.7 | 筛选"只看需更新"：至少一个绑定平台满足判定的章节出现（REQ-03 F3.19–F3.20）。 |
| F4.8 | 编辑页右侧各平台状态卡同样使用该判定，保存后即时刷新（REQ-02 F2.19）。 |
| F4.9 | 看板统计的"需更新"计数与详情页使用**同一判定函数/口径**（REQ-06）。 |
| F4.10 | 对"需更新"章节，提供清除方式：「标记已发布（更新为当前版本）」——用户确认已把新版同步到平台后点击，`published_hash` 更新为当前值。 |
| F4.11 | 只读取已入库的 `content_hash` 判定，不在渲染时重新读文件算 hash（性能；同步负责保鲜）。 |

## 6. 页面与交互

原型：小说详情、章节编辑、总览看板（见 [README「UX 基准」](README.md)）。

- 详情页徽标：↻ 橙色，文案"需更新"；点击在行下方展开操作条（REQ-03 F3.12），`platform_url` 有值时含"打开链接"。
- 工具栏筛选"只看需更新 N"；结果为空时显示"所有已发章节都是最新的"。
- 编辑页右侧平台状态卡：说明"本地内容已变更，与平台已发版本不一致。覆盖会重新审核，请确认已定稿"；审核中被改稿时说明"本地内容已变更，待审核结束后再覆盖"。保存后刷新；未保存的改动不影响徽标。
- 看板卡片：每平台一行"已发 X · 审核中 W · 需更新 Y · 未发 Z"（有丢失时加"丢失 K"），需更新 > 0 时该项橙色加粗（REQ-06 §6）。

## 7. 数据

不新增字段。使用：
- `chapter.content_hash`
- `publication.status`、`publication.published_hash`

## 8. 异常场景

| 场景 | 期望行为 |
|---|---|
| 文件丢失 | 显示"文件丢失"，不判需更新 |
| `content_hash` 为空（尚未同步成功） | 不判需更新（避免误报）；提示需重新扫描 |
| 章节文件被改成与已发版本完全相同 | 自动恢复为"已发布" |
| 仅 CRLF/LF 切换或首尾空白变化 | 不触发需更新 |
| 多平台状态不一致 | 各平台独立显示 |

## 9. 验收标准

- **AC4.1** **Given** 某章在番茄标记已发，**When** 未改内容，**Then** 徽标为"已发布"。
- **AC4.2** **Given** 上述章节，**When** 修改正文并保存/重新扫描，**Then** 番茄徽标变"需更新"，看板"需更新"计数 +1。
- **AC4.3** **Given** 仅把换行符 LF↔CRLF 或增删首尾空白，**Then** 不出现"需更新"。
- **AC4.4** **Given** "需更新"章节，**When** 内容改回与已发版本一致，**Then** 自动恢复"已发布"。
- **AC4.5** **Given** "需更新"章节，**When** 点击"标记已发布（更新为当前版本）"，**Then** 徽标回到"已发"，`published_hash` 等于当前 `content_hash`。
- **AC4.6** **Given** 同一章在番茄已更新、起点未更新，**Then** 仅起点显示"需更新"。
- **AC4.7** **Given** 筛选"只看需更新"，**Then** 仅展示至少一个平台"需更新"的章节。
- **AC4.8** **Given** 详情页与看板，**Then** 同一本书的"需更新"数量一致。
- **AC4.9** **Given** 章节文件丢失，**Then** 显示"文件丢失"而非"需更新"。

## 10. 测试建议

- `hash`：LF/CRLF、首尾空白 → 同 hash；行内空白、标点 → 不同 hash。
- `publish.isStale`：覆盖未发布、已发一致、已发不一致、`published_hash` 为空、`file_missing`。
- 集成/手动：改稿 → 需更新 → 标记已发布 → 已发的完整链路。

## 11. 待确认问题

| # | 问题 | 当前假设 |
|---|---|---|
| Q1 | 标记已发前是否先对该章同步一次，确保 hash 最新 | 建议是：成本小，避免记录陈旧 hash。 |
| Q2 | hash 是否包含章节标题 | 包含 **H1 标题**（它就是发布到平台的标题），不含文件名；修改 H1 标题触发需更新，与番茄发布技能的幂等判定一致。 |
| Q3 | 是否需要查看"相对已发版本改了什么"（diff） | MVP 不做；因不存已发正文快照，无法 diff。若要做，需在标记已发时存正文快照（会改变"数据库不存正文"的原则），列为后续。 |
| Q4 | 是否允许用户对某章"忽略本次更新" | MVP 不做；用「标记已发布（更新为当前版本）」代替。 |
| Q5 | 审核中的章节被本地改稿，如何呈现 | 显示「需更新」，并提示"平台审核中暂不能修改，待审核结束后再覆盖"（REQ-03 F3.23）。 |
